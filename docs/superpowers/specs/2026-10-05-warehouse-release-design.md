# 主仓库事务放生

用户已确认并要求严格实施：主仓库单只与批量放生；复用已有选择与操作栏；一次确认；整批成功或整批保留；无回收站；提交后立即刷新一次清单；不修改游戏存档。

## 数据边界

记录元数据、原始实体和工作实体保存为同一个 SQLite 行，放生在一个数据库事务中删除所有确认对象。SQLite 使用 DELETE journal、FULL synchronous、secure_delete 和自动回收空闲页；保证应用数据的事务性，不承诺闪存安全擦除。

原仓库从 record.json、original.pkm、working.pkm 迁移：先在一个事务内导入，校验数量、元数据与两份字节数据，再提交。提交前不删除源文件。提交后按持久化清理清单删除已验证的旧文件，崩溃后可续清理，不能重新导入已删除记录。旧文件未清理完成时阻止编辑和放生，防止声称清除而留下旧副本；不会创建回收站或长期备份。

保持 LocalRepository 的上传、读取、编辑、合法化、丢弃编辑与传送入口。所有实体读取改用仓库 API，不保留数据库之外的仓库实体副本。记录每次修改递增 Revision；放生按确认时的 ID 与 Revision 校验，变化或缺失导致整批回滚。

## 交互

现有选中状态和高亮共用。主仓库详情使用“选择／取消选择”；长按菜单添加“放生”。现有多选栏并列“下载”和“放生”，不增加独立页面或选择模式。确认显示数量、名称、等级以及不可恢复说明；长名单滚动，取消不写数据。执行期间禁用重复确认、选择、编辑、筛选和下载，不使用传送动画。

成功后重新读取完整仓库，保留有效分页和未删除的选择，清空被删除记录的传送状态；一次刷新数量与清单。失败回滚，提示整批保留；中断前未提交则恢复全部，提交后则删除结果持久保留。
